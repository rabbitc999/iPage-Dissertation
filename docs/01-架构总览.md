# 01 · 架构总览

## 1. 这套系统解决什么问题

传统写法里，加一张业务表的成本是：建表 SQL → 实体类 → Mapper → Service → Controller → 前端列表页 → 前端表单 → 权限判断 → 审计日志。
九处重复劳动，且每一处都可能写错或漏写。

iPage-IMS 把它压缩成**一处**：写一个模型类。

```java
@ModelClass(name = "部门", table = "ims_department", ...)
public class Department {
    @ModelField(column = "dept_id", type = FieldType.MODEL_ID) public String id;
    @ModelField(column = "dept_name", text = "部门名称")        public String name;
}
```

上面这 4 行，换来的是：建表语句、`/api/models/department` 全套接口、前端「部门」菜单与页面、
表格列与表单字段、必填校验、枚举下拉、关联下拉、权限拦截、审计记录。

**代价**：所有模型共用同一套页面形态。需要非常规交互时，才写自定义页面（见 06）。

## 2. 分层结构

空库启动只创建超级管理员及内置角色权限。日常在 Vue 界面管理业务数据与 AI 模型，后端负责模型配置、密钥解密、附件存储和服务端授权。开发时 Vite 提供热更新，`/api` 仍由 Spring Boot 处理。

```
┌──────────────────────────────────────────────────────────────┐
│  浏览器  Vue 3 (web/)                                         │
│  ├─ 通用页 ModelView.vue   ← 按 schema 渲染表格/表单           │
│  └─ 专用页 Dashboard / Permissions / Ai / Profile             │
└───────────────────────────┬──────────────────────────────────┘
                            │ JSON over HTTP (Bearer token)
┌───────────────────────────▼──────────────────────────────────┐
│  Web 层 (web/)                                                │
│  AuthController  MetaController  ModelController              │
│  RoleController  StatsController  AiController  ViewConfig    │
│  统一入口：GlobalExceptionHandler 把一切异常变成 {"message":...} │
└───────────────────────────┬──────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────┐
│  业务装配层                                                    │
│  security/  登录、令牌、密码、请求拦截、权限注解                 │
│  meta/      模型注册表、schema 下发                            │
│  service/   CrudService（核心）、ModelHook、AuditService        │
│  ai/        AiEngineManager（AI 会话与工具装配）                │
└───────────────────────────┬──────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────┐
│  框架层 libs/                                                  │
│  ipage           注解 → 元数据 → SQL；建表/补列；分页查询        │
│  embed-ai-chat   AI 会话、工具调用、MCP stdio 客户端、Skill     │
└───────────────────────────┬──────────────────────────────────┘
                            │  JDBC
                     H2 / MySQL / PostgreSQL
```

**依赖方向严格向下**：`web → service → ipage`。反之不允许——
`service` 不知道 HTTP 存在，`ipage` 不知道这个项目存在。这样框架才能被替换。

## 3. 一次请求的完整生命周期

以 `GET /api/models/employee?kw=陈` 为例：

```
1. Tomcat 收到请求
2. AuthInterceptor.preHandle
   ├─ 读 Authorization: Bearer xxx
   ├─ TokenService.verify → 验签 + 验过期 → 得到 {uid, ver}
   ├─ AuthService.load(uid)            ← 每次都读库，不是从令牌里取权限
   │    ├─ 查 sys_user，比对 tokenVersion（不一致说明改过密码/被踢）
   │    ├─ 查 sys_user_role → sys_role       → 等级、数据范围
   │    └─ 查 sys_role_permission → sys_permission → 权限点集合
   ├─ UserContext.set(loginUser)       ← ThreadLocal
   └─ 校验方法上的 @RequireLevel / @RequirePermission
3. ModelController.page → CrudService.page
   ├─ ModelRegistry.requireMeta("employee")   ← 类名首字母小写
   ├─ requireView：等级够不够看这张表
   ├─ applyScope：按 DataScope 追加 deptId / createBy 条件
   ├─ applyKeyword：先查匹配的主键集合，再 IN 过滤
   ├─ applyFilters：f_ 字段 / op_ 操作符
   ├─ applySort：字段必须存在且有查看权限，否则退回主键
   └─ sql.selectPage(query)  → ipage 生成 SQL
4. toRow：字段级权限过滤 + 枚举转中文 + 关联转 {id,label} + 日期格式化
5. 返回 JSON；异常由 GlobalExceptionHandler 统一成 {"message","status"}
6. AuthInterceptor.afterCompletion → UserContext.clear()   ← 必须清，否则线程池串号
```

**关键点：权限每次请求都从库里重建。** 令牌里只有 `uid / ver / exp`。
好处是管理员改了权限立刻生效、停用账号立即踢下线；代价是每请求多几条查询（有需要再加缓存）。

## 4. 三个核心抽象

### 4.1 ModelMeta —— 模型的运行时元数据

`libs/ipage/reflect/ModelMeta.java`。解析注解后的结果，是**表名与列名的唯一来源**：

```java
meta.table()        // "ims_employee"
meta.idColumn()     // "emp_id"
meta.idField()      // 主键字段描述符
meta.fields()       // 全部字段
meta.field("deptId")// 按 Java 字段名取（不是列名）
meta.display(entity)// 按 @ModelClass(text="${name}") 渲染显示名
```

**不要**在业务代码里写 `"ims_employee"` 或 `"emp_id"`，一律走 `ModelMeta`。

### 4.2 CrudService —— 唯一的数据出入口

所有读写（页面、AI 工具、脚本）都经过它，因此权限、数据范围、审计只有一份实现。
它不做"某个模型的特殊逻辑"——那交给 `ModelHook`。

### 4.3 ModelHook —— 模型的个性化扩展点

五个时点：`beforeCreate / afterCreate / beforeUpdate / afterUpdate / beforeDelete`。
认领方式是 `supports(Class<?>)`。现有两个实现：

- `UserHook`：密码散列、角色同步、防删自己/最后一个超管；
- `AiConfigHook`：MCP/Skill 变更后发事件，让 AI 引擎重建会话。

## 5. 设计取舍（以及为什么拒绝另一些做法）

| 决策 | 选择 | 拒绝的方案 | 原因 |
| --- | --- | --- | --- |
| 权限粒度 | 等级 + 权限点 + 数据范围 | 纯 URL 白名单 | 白名单无法表达"能看本部门"，且加接口就要改配置 |
| 行过滤位置 | 集中在 `CrudService` | 每个查询自己加条件 | 散落必然漏；漏一处就是越权 |
| 主键 | UUID 字符串 | 自增 BIGINT | 不可枚举、可离线生成、合并安全（详见 02） |
| 令牌 | 无状态 HMAC + 版本号 | 服务端 Session | 免共享存储；版本号解决"改密码旧令牌还在"的问题 |
| 前端渲染 | schema 驱动 | 每个模型写一套页面 | 加字段零改动；代价是交互形态统一 |
| 建表 | 启动时按模型同步 | Flyway/Liquibase 迁移脚本 | 单人小项目维护迁移脚本成本高于收益；大团队仍建议引入 |
| 服务端渲染 | 无，纯 SPA | Thymeleaf | 与嵌入式 AI 控制台、富交互页面不搭 |
| AI 权限 | 复用登录用户身份 | 给 AI 一个管理员身份 | 后者等于绕过全部权限体系 |

## 6. 技术选型清单

| 层 | 选型 | 为什么 |
| --- | --- | --- |
| 运行时 | Java 17 | Spring Boot 3 最低要求，LTS |
| Web | Spring Boot 3.3 + 内嵌 Tomcat | 单 jar 部署，无需外部容器 |
| 持久 | iPage + JDBC | 不引 ORM，SQL 可控、方言可切换 |
| 数据库 | H2（默认）/ MySQL / PostgreSQL | H2 免安装，切库只改 profile |
| 前端 | Vue 3 + Vite | 编译快、无运行时依赖负担 |
| 状态 | 组合式 API + reactive | 这个规模不需要 Pinia |
| 路由 | vue-router，`createWebHashHistory` | hash 路由不需要服务端 SPA 回退配置 |
| AI | OpenAI 兼容协议 + MCP stdio | 换模型只改 base-url/model |

## 7. 代码规模与分布

| 模块 | 文件数 | 说明 |
| --- | --- | --- |
| `libs/ipage` | 39 个 Java | 上游源码，不修改 |
| `libs/embed-ai-chat` | 1 个大类（~1100 行） | 上游源码，不修改 |
| `server` | 55 个 Java | 本项目业务代码 |
| `web/src` | 16 个文件 | 6 页面 + 2 组件 + api/store/router |

`server` 里最值得先读的三个文件：

1. `service/CrudService.java` —— 所有 CRUD 的实现，看它等于看懂一半系统；
2. `security/AuthService.java` —— 权限快照怎么算出来的；
3. `meta/MetaService.java` —— 前端拿到的 schema 是怎么拼的。

## 8. 后续演进建议（按性价比排序）

1. **加集成测试**：`spring-boot-starter-test` 已引入但没有用例。优先补"登录 → 建表 → CRUD → 越权 403"。
2. **引入 Flyway**：当表结构开始有"改类型/删列"需求时，iPage 的同步能力不够用了。
3. **权限缓存**：`AuthService.load()` 每请求 3~4 条查询，用户量上来后可加 30 秒本地缓存 + 变更事件失效。
4. **对象存储**：当前没有附件能力，模型里加 `fileId` 需要配套上传接口。
5. **审计可视化**：`sys_audit_log` 已有数据，但只有列表，缺按模型/操作人聚合的看板。
