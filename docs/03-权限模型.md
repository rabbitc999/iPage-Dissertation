# 03 · 权限模型

> 三层：**模型等级**（能不能进这张表）× **权限点**（能不能做这个动作）× **数据范围**（能看哪些行）。
> 三层同时满足才放行——这是"默认拒绝"的实现方式。

---

## 1. 全景

```
登录  →  sys_user_role  →  sys_role { level, data_scope }
                              ↓
                        sys_role_permission → sys_permission { code }
                              ↓
                    LoginUser { id, level, permissions, dataScope, deptId }
                              ↓
    ① 等级：@ModelClass(look/edit/delete) 与用户 level 比大小     → 能否进入该表
    ② 权限点：@RequirePermission("ai:use") 与 permissions 比对     → 能否执行该动作
    ③ 数据范围：DataScope 决定 SQL 里加不加 deptId / createBy 条件  → 能看哪些行
```

三个例子：

| 场景 | ① 等级 | ② 权限点 | ③ 数据范围 | 结果 |
| --- | --- | --- | --- | --- |
| staff 看用户表 | `look=ADMIN(3)` > `1` | — | — | 403「没有查看「用户」的权限」 |
| manager 看员工 | `look=LEAST` 通过 | — | `DEPT` → `dept_id = 本人部门` | 只看本部门员工 |
| admin 调 AI | 通过 | 有 `ai:use` | — | 正常对话 |

## 2. 第一层：模型等级

### 2.1 等级表

| 等级 | 值 | 约定用途 |
| --- | --- | --- |
| `LEAST` | `Integer.MIN_VALUE` | 不限制，人人满足 |
| `INHERIT` | `MIN+1` | **仅用于字段注解**的默认值（继承模型） |
| `STUDENT` | 0 | 只读级 |
| `NORMAL` | 1 | 普通用户 |
| `TEACHER` | 2 | 主管/审核者 |
| `ADMIN` | 3 | 管理员 |
| `SUPER_ADMIN` | 4 | 超管 |
| `FORBIDDEN` | `Integer.MAX_VALUE` | 谁都不满足（字段级禁用） |

比较方式：`user.level >= required.level`（`LoginUser.reaches()`）。

### 2.2 用户等级怎么来

`AuthService.snapshot()`：查用户所有角色的 `level`，**取最大值**。
所以"给某人加一个临时高权角色"就等于临时提权，去掉即恢复。

没有任何角色时等级为 `0`（`STUDENT`），即"能看 LEAST 的表，不能改"。

### 2.3 字段级权限

```java
@ModelField(column = "password_hash", look = false, editPermission = ModelPermission.FORBIDDEN)
public String passwordHash;
```

- `look = false`：不出现在 `toRow()` 的结果里（**不是前端隐藏，是服务端根本不下发**）；
- `lookPermission = ADMIN`：只有管理员能看到这个字段；
- `editPermission = FORBIDDEN`：请求体里带了也忽略。

> 判断字段权限的地方**只有 `CrudService.toRow()` 和 `applyBody()` 两处**。
> 新增输出路径（比如导出接口）时必须复用同样规则，否则会出现字段泄露。

## 3. 第二层：权限点

权限点解决"同一等级下更细的开关"，例如两个管理员，一个能改角色一个不能。

### 3.1 现有权限点

| 编码 | 名称 | 分组 | 用在哪 |
| --- | --- | --- | --- |
| `system:user:manage` | 用户管理 | 系统管理 | 预留，用户表本身由 `ADMIN` 等级控制 |
| `system:role:manage` | 角色与权限 | 系统管理 | `RoleController` 的写接口 |
| `system:audit:view` | 审计日志 | 系统管理 | 预留 |
| `ai:use` | 使用 AI 助手 | 智能助手 | `AiController.chat` |
| `ai:manage` | 管理 MCP 与 Skill | 智能助手 | `AiController.reload` |

### 3.2 代码里怎么用

```java
@RequirePermission("system:role:manage")     // 注解，方法或类上
public Map<String, Object> create(...) { }

if (user.has("system:role:manage")) { ... }  // 代码里判断
```

`LoginUser.has()` 对 `SUPER_ADMIN`（等级 ≥ 4）**恒为 true**，避免超管被自己锁死。

### 3.3 特殊形态：`model:{key}:{edit|delete}`

`CrudService.requireEdit/requireDelete` 还会检查 `model:employee:edit` 这样的权限点：

```java
if (!user.reaches(meta.editPermission()) && !user.has("model:" + key + ":edit")) {
    throw ApiException.forbidden(...);
}
```

含义：**等级不够时，可以被一个精确权限点"特批"**。目前没有界面入口，
属于预留能力（想用就在 `sys_permission` 里加一条，再在角色矩阵里勾选）。

## 4. 第三层：数据范围（行过滤）

### 4.1 三档语义

| 档位 | 条件 | 依赖字段 | 缺字段时 |
| --- | --- | --- | --- |
| `ALL` | 不加条件 | — | — |
| `DEPT` | `dept_id = 当前用户 deptId` | `deptId` | 不过滤（放行） |
| `SELF` | `create_by = 当前用户 id` | `createBy` | 不过滤（放行） |

用户的实际范围 = 其所有角色里**最宽**的那个（`ALL > DEPT > SELF`）。

### 4.2 两处实现必须同步

| 场景 | 方法 | 形态 |
| --- | --- | --- |
| 列表 / 计数 | `CrudService.applyScope()` | 生成 SQL 条件 |
| 单行读/改/删 | `CrudService.visibleRow()` | 内存比较 |

漏改任何一处都会出现"列表里看不到，但知道 ID 就能改"的越权洞。

### 4.3 为什么行过滤不写在注解里

曾考虑 `@RowScope("dept")` 之类。放弃的原因：

1. 行过滤是**查询语义**，会随需求演进（"本部门及下级部门""本人参与的"）；
2. 写进注解就把可配置的东西变成了编译期常量；
3. 集中在 `CrudService` 一处，审计代码时只需要看一个文件。

## 5. 认证：令牌与失效

### 5.1 令牌形态

```
base64url({"uid":"<uuid>","ver":3,"exp":1767225600}) + "." + base64url(HMAC-SHA256(payload))
```

- 无状态，服务端不存 session；
- **payload 里没有角色和权限**，每次请求都读库重建 → 改权限立即生效；
- `ver` 与 `sys_user.token_version` 比对，不一致直接 401。

### 5.2 什么时候旧令牌失效

| 操作 | 效果 |
| --- | --- |
| 用户改自己的密码 | `token_version + 1` → 所有旧令牌失效，返回新令牌 |
| 管理员重置他人密码 | 同上，目标用户被踢下线 |
| 停用账号 | 下次请求 `AuthService.load()` 抛 403 |
| 退出登录 | `token_version + 1` |
| 更换 `IMS_SECRET` | 全部令牌验签失败（全局强制重登） |

### 5.3 密码存储

`security/PasswordHasher`：PBKDF2-HMAC-SHA256，210,000 次迭代，每用户 16 字节随机盐，
存储 `pbkdf2$迭代次数$盐$散列`，比较用 `MessageDigest.isEqual`（常量时间）。

- **不是加密，是单向散列**：系统没有任何地方能取回原密码；
- 迭代次数随记录保存，调高参数不会让老密码失效；
- 登录成功时若发现旧哈希迭代次数偏低，自动重算升级（用户无感）。

## 6. 角色与权限的维护方式

### 6.1 界面

「权限 → 角色与权限」页：左侧角色列表，右侧按分组勾选权限点。
保存调 `PUT /api/roles/{id}/permissions`，整体替换（先删后插）。

### 6.2 内置角色

| 编码 | 等级 | 数据范围 | 说明 |
| --- | --- | --- | --- |
| `SUPER_ADMIN` | 4 | ALL | 拥有全部权限点，`has()` 恒真 |
| `ADMIN` | 3 | ALL | 管理用户、角色与数据 |
| `MANAGER` | 2 | DEPT | 只看本部门 |
| `STAFF` | 1 | SELF | 只看自己创建的 |

`builtin = true` 的角色不允许删除。新增角色走「权限」页的"新建角色"。

### 6.3 几个防呆规则（`UserHook`）

- 不能删除当前登录账号；
- 不能删除最后一个超级管理员；
- 不能停用当前登录账号；
- 账号名唯一。

## 7. 加权限的正确姿势（决策表）

| 需求 | 做法 |
| --- | --- |
| 新表，只有管理员能进 | `@ModelClass(edit=ADMIN, delete=ADMIN, look=ADMIN)` |
| 新表，所有人能看、主管能改 | `look=LEAST, edit=TEACHER, delete=ADMIN` |
| 某字段只有管理员看得到 | `@ModelField(lookPermission = ModelPermission.ADMIN)` |
| 某字段谁都不能改（如余额） | `@ModelField(editPermission = ModelPermission.FORBIDDEN)` |
| 新增一个独立功能接口 | 建权限点 + `@RequirePermission("biz:xxx")` |
| 让某个角色只看自己部门 | 角色表 `data_scope = DEPT`（模型需有 `deptId`） |
| 让某个角色只看自己创建的 | 角色表 `data_scope = SELF`（模型需有 `createBy`） |

> 不要用"多加一个角色"来解决"多一个按钮"的问题——那是权限点的职责。
> 也不要用权限点解决"整张表能不能进"——那是等级的职责。

## 8. AI 工具与高风险运维

AI 请求须先通过 `ai:use`、模型最低角色等级、密钥部门/账号名单。实际工具操作同时受模型工具上限、本轮所选档位、业务模型权限和行范围约束。删除需要本轮「所有权限」。附件关联至少需要「可添加」，同时更新业务字段需要「可添加编辑」，网页对话还须开启本轮「文件写入」。详见 [AI 集成](07-AI集成-MCP与Skill.md)。

运行日志策略和清空系统数据由服务端用 `@RequireLevel(SUPER_ADMIN)` 校验。清空必须重新验证密码，并持短期确认令牌完成二次确认。

## 9. 已知限制

1. **部门数据范围不含下级部门**（只有 `dept_id = 我的部门`）。需要树形时改 `applyScope()` 为 `IN (子树)`。
2. **没有字段级的"写"校验以外的数据脱敏**，如手机号中间四位打码；
   需要时在 `toRow()` 里加变换，注意别影响编辑（编辑走 `get()` 同一路径）。
3. **权限变更无审计**：`RoleController` 的授权动作没写 `sys_audit_log`，
   只有模型 CRUD 自动审计。需要合规时补一条。
4. **令牌无法主动吊销单个设备**，只能"全部作废"（版本号机制）。


## 审计日志的独立授权

审计日志使用 `system:audit:view`（查看审计日志）和 `system:audit:delete`（删除审计日志）两个独立权限点。管理员在“角色与权限”中按角色勾选；通常为需要删除日志的角色同时勾选查看和删除。只有查看权限时可以查看，页面不显示删除操作；没有查看权限时不显示审计日志菜单。通用接口和 AI 工具复用同一套后端校验，角色等级和通用 `model:auditLog:*` 权限不能替代这两个权限点。超级管理员沿用系统规则，默认拥有全部权限。

启动时（`ims.seed=true`）会为已有数据库幂等补齐权限点，不自动给已有角色授予新增删除权限，也不恢复已撤销的授权。新库的系统管理员默认具有查看权限，删除权限需另行授予。无需重建数据库。运行日志保留策略仍由原有超级管理员入口管理。
